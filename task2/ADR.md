### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Время отклика для всех интерфейсов ≤ 1 секунды в 99.99% случаев |
| 2 | Ожидаемый показатель p98 = 0.3 секунды |
| 3 | Масштабирование до 40 000+ заказов в день в перспективе |

| 6 | Eventual consistency допустима для read-модели истории покупок (данные могут отставать на секунды) |

### **Решение**

#### Выбранный подход: **CQRS (Command Query Responsibility Segregation)**

Для реализации сценария «Просмотр истории покупок» вводится отдельный **Order History Service** — read-сервис, построенный по паттерну CQRS.

**Суть решения:**

1. **Order History Service** подписывается на события из Kafka:
    - `OrderCreated` — создание записи о заказе (состав, суммы, адрес)
    - `OrderCancelled` — обновление статуса заказа на «Отменён»
    - `InventoryReserved` — обновление информации о резервировании товаров
    - `PaymentSucceeded` / `PaymentFailed` — обновление способа и статуса оплаты
    - `DeliveryRequested` — обновление способа доставки, трек-номера
    - `DeliveryStatusUpdated` — обновление статуса доставки (передан в доставку, доставлен)

2. На основе этих событий сервис строит **денормализованную read-модель** в собственной базе данных (MongoDB), где каждый документ содержит полную информацию о заказе:
    - ID заказа, дата создания
    - Список товаров (название, количество, цена)
    - Итоговая сумма
    - Способ и статус оплаты
    - Способ доставки, трек-номер, статус доставки
    - Финальный статус заказа

3. **API Gateway** маршрутизирует запросы к Order History Service для:
    - `GET /order-history` — список заказов покупателя
    - `GET /order-history/{orderId}` — детали конкретного заказа
    - `GET /order-history/{orderId}/receipt` — скачивание чека

4. Операции записи (оставить отзыв, повторить заказ) маршрутизируются на соответствующие write-сервисы:
    - Отзыв в Catalog Service
    - Повторный заказ в Cart Service / Order Service

**Почему MongoDB:**
- Документная модель идеально подходит для хранения денормализованного представления заказа
- Высокая скорость чтения по ключу (userId + orderId)
- Гибкая схема позволяет легко добавлять новые поля (промо, возвраты, лояльность)

**Почему CQRS:**
- Данные для отображения разбросаны по 4+ микросервисам — собрать их синхронно за 0.3 сек нереалистично при росте нагрузки
- Система уже event-driven (Kafka) — проекция событий в read-модель — естественное расширение
- Read-модель можно масштабировать независимо от write-сервисов
- Один запрос к одному сервису - предсказуемая латентность

### **Альтернативы**

#### Альтернатива 1: API Composition

API Composition предполагает введение сервиса-композера (или использование API Gateway), который при каждом запросе на историю покупок синхронно вызывает Order Service, Payment Service, Delivery Service и Catalog Service, агрегирует результаты и возвращает ответ.

**Плюсы:**
- Простота реализации — не нужна отдельная read-модель и подписка на события
- Данные всегда актуальны (strong consistency)
- Меньше инфраструктурных компонентов

**Минусы:**
- Время отклика = сумма задержек всех вызываемых сервисов (или максимальная при параллельных вызовах); при 4 сервисах сложно гарантировать p98 ≤ 0.3 сек
- Доступность API = произведение доступностей каждого из сервисов — одна деградация «ломает» весь ответ
- При росте нагрузки (40 000+ заказов/день) каждый read-запрос создаёт нагрузку на write-сервисы
- Сложность обработки частичных отказов (что показывать, если Delivery Service не ответил?)

#### Альтернатива 2: Event Sourcing

Вместо хранения текущего состояния хранить полный лог событий и восстанавливать состояние заказа при каждом запросе.

**Плюсы:**
- Полная аудируемость — можно восстановить состояние заказа на любой момент времени
- Возможность перестраивать проекции «с нуля»
- Естественно интегрируется с EDA

**Минусы:**
- Избыточная сложность для данного сценария — для «Просмотра истории» достаточно текущего состояния, полный лог не нужен
- Необходим snapshot-механизм для заказов с большим числом событий
- Высокий порог входа для команды — усложнение отладки и поддержки
- Более сложная миграция схемы событий

#### Альтернатива 3: CQRS + Event Sourcing

Комбинация: Event Sourcing для хранения событий и CQRS-проекция для read-модели.

**Плюсы:**
- Все преимущества обоих подходов
- Максимальная гибкость и аудируемость

**Минусы:**
- Максимальная сложность реализации и сопровождения
- Для MVP-сценария «Просмотр истории» избыточна
- Оправдана при появлении требований к аудиту, версионированию состояний заказов

### **Недостатки, ограничения, риски**

| № | Категория | Описание |
| :-: | :- | :- |
| 1 | **Eventual Consistency** | Read-модель обновляется с задержкой (обычно секунды). Покупатель может не увидеть только что оформленный заказ в истории. Риск минимален, т.к. сценарий «История покупок» по своей природе не требует мгновенной консистентности |
| 2 | **Дополнительная инфраструктура** | Появляется новый сервис (Order History Service) и новая БД (MongoDB), что увеличивает операционную нагрузку на команду DevOps |
| 3 | **Дублирование данных** | Данные о заказах хранятся и в Order DB, и в Order History DB. Нужен механизм контроля расхождений  |
| 4 | **Эволюция схемы событий** | При изменении формата событий необходимо обеспечить обратную совместимость, иначе Order History Service перестанет корректно обновлять проекцию |
| 5 | **Восстановление проекции** | При сбое или необходимости перестроить read-модель с нуля нужен механизм replay событий из Kafka  |
| 6 | **Масштабирование** | При росте объёма заказов MongoDB-коллекция может потребовать шардирования по userId — нужно заложить это в дизайн с самого начала |
